# DramaForge — AI ショートドラマ自動生成プラットフォーム

[English](README.md) · [中文](README.zh.md) · **日本語**

小説や脚本を、絵コンテ化・画像生成・動画生成・音声合成まで通して、納品できるショートドラマに仕上げます。サーバー側はプロンプト組み立て、タスク編成、課金、複数ベンダーの取りまとめを担当し、メディアのレンダリングは Electron クライアントのローカルで行います。サーバーはメディアのバイトを一切保存しません。

> このリポジトリは**秘匿情報を除去したソース公開版**です。実際のホスト名・ドメイン・SSH 鍵名はプレースホルダーに置換済みで、本番の認証情報は含みません。元リポジトリの 291 コミットの履歴は書き出しておらず、ここは単一スナップショットです。

## 何を解決するか

実写ショートドラマの 1 シーズンは 35 話・1000 カット超です。手作業では回らず、スクリプトを繋いだだけでは再生に耐える映像になりません。本プラットフォームはその中間工程を工学化します——次の 4 点を解かない限り納品に到達しません：

| ボトルネック | 解かない場合 | 本リポジトリでの扱い |
|---|---|---|
| **1000 カットの状態管理** | どのカットのプロンプトを変えたか、どの話を再実行したかを誰も追えず、1 箇所の修正で全体をやり直すことになる | 5 ステージがそれぞれ自分のテーブルに書き、前段の成果物だけを読む。どのステップも単独で再実行できる |
| **カット間で人物が変わる** | 同じ人物が第 1 話と第 30 話で別の顔になり、視聴者は即座に気づく | キャスティング固定：参照画像 1 枚で人物 1 人を固定。再生成は上書きせず新しいリビジョンを作る。カットは名前ではなくアセット ID を参照する |
| **動画モデルが不安定** | 数百タスク中の 1 回のレート制限で全体が失敗し、計算資源と待ち時間のコストがクライアントに集中する | key プールのローテーション、失敗時のクールダウン、タスクリース＋ハートビート、再開可能な実行。生存判定はハートビートではなく claim の上限で行う |
| **顧客素材をクラウドに置けない** | 私有の素材をサーバーに置くと、ストレージ費用・外向き通信・コンプライアンス上のリスク が同時に膨らむ | 薄いサーバー：サーバーは AI key と DB メタデータのみを保持し、メディアのバイト列はすべて顧客のローカルディスクに残る |

結果として、35 話・1246 カット・71 アセットのドラマが、原文入力から完成カット搬出まで再実行可能なパイプラインになります。一度きりの手作業ではなく。

## 業務フロー

製品全体が 5 段階のパイプラインです。各段階はひとつのことだけを行い、結果を 1 つのテーブルに書き、次の段階はそのテーブルから読みます。そのためどこで止めても、直してから続きを流せます。

| 段階 | 画面で行うこと | 書き込み先 |
|---|---|---|
| **1 入力** | 小説・脚本の原文を取り込む。または参照動画を投入し、人物・場景・カット構成を先に抽出させる | `projects.novelText`、`projects.artStyle`、`projects.artStylePrompt` |
| **2 脚本分析** | 話数に分割し、場景と人物を抽出、感情の起伏も算出。改写稿は原文と並べて段落単位で確認 | `episodes.scenes[]`（`scene_id`/`characters[]`/`visual_style`）、`episodes.emotionArc` |
| **3 アセット設定** | 人物・小道具・場景の 3 種類を個別に確定。人物 1 人につき参照画像 1 枚。作り直すと新しい版が残り、旧版も消えない | `assets`（`kind` = `CHARACTER`/`PROP`/`LOCATION`）、`asset_image_revisions` |
| **4 絵コンテ設計** | カット 1 行につき、尺・プロンプト・目的タグ・感情の位置・モンタージュ種別・音声種別、参照するアセット | `shots`（`referencedAssets`、`purposeTag`、`aspectRatio` 既定 9:16） |
| **5 制作** | カットごとに候補を生成 → 採用 → 合成 → 書き出し。一括レンダリングは長時間タスクで、画面を閉じても継続 | `tasks`、`tasks_events`、`materials`、`render_jobs` |

同じデータの上に 3 つのライブラリがあります。**完成品ライブラリ**（プロジェクト横断の完成品）、**カットグループライブラリ**（最後まで生成できたグループを プロジェクト → 話数 でまとめたもの）、**メディアライブラリ**（クライアント側のローカル動画・画像・音声）。

### データオブジェクト

| テーブル | 内容 |
|---|---|
| `projects` | プロジェクト単位：原文、脚本 JSON、画風の固定、バージョン（楽観ロック） |
| `episodes` | 話数：本文、文字数、状態、`scenes[]`、感情の起伏、既定の視覚スタイル |
| `assets` | アセット：種別、名称、説明、参照画像、メタデータ、バージョン |
| `shots` | カット：連番、尺、プロンプト、目的／感情位置／モンタージュ、参照アセット、選択中の素材、生成状態 |
| `materials` | 1 回の生成で出た候補素材（採用選び用） |
| `tasks` / `tasks_events` | 非同期タスクと進捗イベント（text / image / video / voice の 4 キュー） |
| `render_jobs` | レンダリングジョブ。リースとハートビート付き |
| `billing_ledger` | 課金履歴：元 → クレジット（20% 加算、切り上げ、最小 1 クレジット） |
| `api_configs` | プラットフォーム側のキープール。モデル群ごとにローテーション |

### 全工程に効く 4 つのルール

1. **1 つのカットグループが参照できる人物は 4 人まで。** Volcengine Seedance の推奨では参照人物が 4 人を超えると顔の安定性が落ち、双子や多主体の破綻が出ます。超えたら事前に 400 で弾き、生成後に選び直す運用にはしません。
2. **禁止語のマッピングは 1 か所だけ、3 経路に同時に効く。** アセット画像・場景の立ち位置図・動画生成が同じ `sanitizePromptForModeration()` を通ります。動画経路は LLM の書き換え後にもう一度冪等なすり抜け防止をかけ、禁止語が戻らないようにします。
3. **キープールと同時実行ゲート。** 全体の上限とは別にユーザーごとの枠を設け、失敗したキーはクールダウンして別キーに回し、上流を叩き潰さずキューで待たせます。
4. **レンダリングはリース＋ハートビート。ただしハートビートは生存の証明にならない。** ハートビートは 30 秒ごとに更新し、`reapStale` が期限切れを回収します。しかし固まったジョブもハートビートだけは新しく見えるため、ハートビートを見ない claim 上限を別途設けています。

![フロントエンドのページとコンポーネント構成](docs/assets/frontend-map.svg)

| `/films` | 完成品ライブラリ：プロジェクト横断の完成品 |

## 技術的なポイント

### 4 層のプロンプト組み立て

`domain/prompt/` は責務ごとに 4 層に分かれます。アセット用（人物・場景・小道具）、場景用、カット用、グループ全体のプレビュー用です。各層は自分の区間だけを組み立て、最後に `asset-helpers.ts` がまとめます。

### 審査前のブロック

送審に回る 3 経路（アセット画像・場景の立ち位置図・Seedance 動画）は、送出前に同じ禁止語テーブルを通ります。

```ts
// packages/server/src/domain/prompt/asset-helpers.ts
export const PROMPT_SANITIZATION_MAP: Array<[string, string]> = [
  ['血迹', '污渍'], ['尸体', '倒地身躯'], ['灵堂', '旧堂'], …
];
export function sanitizePromptForModeration(prompt: string) { … }
```

禁止語の追加は表に 1 行足すだけで、3 経路すべてに反映されます。

### 実在人物判定の回避

Volcengine Seedance は「参照画像が実在人物らしい」と入力グループごと拒否します（`InputImageSensitiveContentDetected.PrivacyInformation`）。回避の処理はクライアント側にあります。

1. `gen_face_grid.py` が OpenCV DNN（`res10_300x300_ssd_iter_140000`）と Haar カスケードの 2 系統で顔矩形を求め、15% 外側に広げる；
2. 矩形の内側だけに疎な白いグリッドを描いて元画像と混合。顔が無ければ全画面グリッドに退避；
3. `grid-overlay.ts` が sharp でサイズと容量を抑える：jpeg/png/webp、辺 300–6000 px、最長辺 1280 px、JPEG q88、1 枚 30 MB 未満；
4. Python が無い、またはオフラインのときは全画面グリッドかそのまま透過に退避し、生成を止めない。

### 複数ベンダーのゲートウェイとキープール

`callAI(model, payload, cred, ctx)` という単一の入口から 8 個のプロバイダーアダプターに振り分けます。`gateway/` のコメントには、`image_url` の受け取り方が事業者ごとに違う、Gemini の safety フィールド名が違う、negative prompt 非対応のモデルがある、といった落とし穴が書かれています。

`api-key-pool.ts` がキーのローテーション、失敗時のクールダウン、同時実行の分散を担い、上位の `task/queues.ts` が BullMQ を text / image / video / voice の 4 キューに分けます。

### タスクの耐障害性

動画レンダリングは長時間タスクなので、`render-job-repo.ts` は「リース＋ハートビート」方式を採ります。

- ハートビートは 30 秒ごとにリースを更新し、`reapStale` が未更新のものを回収する；
- ただしハートビートは実行とは独立なので、**固まったタスクはいつまでも「ハートビートが新しい」と表示される**。そこでハートビートを見ない claim 上限を追加した（既定 4 時間、`LONG_VIDEO_REWRITE` は 12 時間）；
- 判定ロジックは純関数に切り出して単体テストを付け、止血は生 SQL ではなく管理 API 経由で行う。

```
packages/
  server/       サーバー：domain（業務）/ gateway（ベンダー）/ task（キュー）/ ai-worker

  shared/       共有型と計算（価格、尺など）

scripts/        デプロイ、ロールバック、診断、クライアント配布
```

## 補足

- 本リポジトリは**サーバーとクライアントのソーススナップショット**です。モデルの重み、ビルド成果物、実際の認証情報は含みません。
- `packages/client/resources/face-models/` の DNN モデルは OpenCV 公式配布の顔検出モデルです。
- デプロイスクリプト内の `YOUR_SERVER` / `your-domain.example.com` / `deploy_key` はプレースホルダーです。置き換えればそのまま使えます。
- `docs/assets/*.svg` は本リポジトリのコードと migrations から起こした図で、**画面のスクリーンショットではありません**。実行可能なフロントエンドのビルドは含まないため、実機のスクリーンショットは「クイックスタート」で一式を立ち上げて取得してください。（本ページの図は英語版。中国語版は *.zh.svg。）
- 本番環境の接続情報は本リポジトリには含まれず、公開リポジトリにコミットしてはいけません。
