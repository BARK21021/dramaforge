# DramaForge C/S 生产服务器容量与极限压测报告

测试日期：2026-07-22（Asia/Shanghai）  
生产地址：`https://your-domain.example.com`  
服务器：2 vCPU / 1.83 GiB RAM / 40 GiB 系统盘  
版本：客户端 1.1.6，服务端 1.1.6 hotfix  
结论等级：**轻量交互通过；真实并发 AI 生成不通过；SSE 连接容量通过但事件实时送达不通过。**

## 1. 执行摘要

本次没有把 50 个付费 AI 请求直接打向生产上游。测试采用临时零积分账号，登录一次后复用合法会话，仅请求只读 API；账号已在测试后删除，生产任务、项目、积分和媒体对象未被修改。

核心实测结果：

- 50 个高活跃闭环客户端：60.74 RPS，1,573 个请求全部成功，P50 44ms、P95 96ms、P99 318ms。
- 200 个闭环客户端：230.37 RPS，P95 223ms，仍然 0 失败。
- 250 个闭环客户端：达到本次最高吞吐 244.28 RPS，P95 上升到 452ms。
- 300 个闭环客户端：吞吐反而下降至 229.47 RPS，P95 上升到 902ms、P99 1,369ms，已经进入 CPU 饱和后的排队区。
- 全程计量请求 31,765 个，计量范围内 5xx、超时和意外鉴权错误均为 0。
- Web 峰值 CPU 107.31%，整机 1 分钟负载峰值 5.54；这是当前 2 vCPU 主机的明确饱和信号。
- 无容器重启、无 OOM、无 Redis 拒绝连接、无 Redis 淘汰、无 PostgreSQL `too many clients`。
- 100 条 SSE HTTP 连接均建立，Redis 客户端从 8 增至 108；但连接在较长时间内收不到首个 `connected` 事件，生产 Nginx 缓冲配置与 SSE 响应头未正确保证实时刷新。测试端主动断开后出现的 100 个 HTTP 499 是预期清理结果。

因此，本次可以确认：**50 人同时在线、浏览项目、读取任务、余额和成片列表，服务器有明显余量。** 但不能据此确认 50 人同时进行 Seedance 视频、长视频转绘、剧本分析或资产生成；这些路径的硬瓶颈在上游限流、未统一排队和内存整体缓冲，远早于本次测得的 HTTP 极限。

## 2. 容量判定

| 能力 | 判定 | 说明 |
|---|---|---|
| 50 人同时轻量浏览/查询 | 通过 | 实测 P95 96ms、0 失败；测试流量约 60.74 RPS，已经高于 50 个正常创作者的常见稳态请求率 |
| 50 条 SSE 长连接 | 连接容量通过 | Redis/Nginx/Web 能维持连接，资源稳定 |
| SSE 进度实时到达 | 不通过 | 100 条连接未及时收到首事件，需关闭代理缓冲并修复生命周期 |
| 50 人同时普通资产生图 | 不满足“同时完成” | 生产同类 Worker 实际并发为 1，只能可靠排队，尾部等待可能接近半小时以上 |
| 50 人同时 Seedance | 不通过 | 视频路由存在同步直连上游路径；模型目录写 10 RPM/并发 2，但服务端未执行全局门控 |
| 50 人同时长视频转绘/解析 | 明确不通过 | Web 仅 384MiB，多条接口会把最高 100MiB 文件整体变成 ArrayBuffer/Buffer |
| 50 人同时携带多张参考图生成视频 | 明确不通过 | 多图以 Base64 JSON 整体进入 Web，再次序列化转发，少数大请求就可能触发内存上限 |
| 生产轻量 API 安全运行上限 | 建议不超过本次 150 VU 档 | 约 175 RPS、P95 186ms；保留吞吐、真实大字段和后台任务余量 |
| 本次合成流量饱和点 | 约 244 RPS | 250 VU 达到吞吐峰值；300 VU 吞吐下降且延迟翻倍 |

“150 VU”不是产品可以承诺的真实用户数。临时测试账号没有大型项目内容，且所有 VU 复用同一会话，数据库缓存命中率偏高；真实项目列表会返回 `novelText`、`scriptData`、episode content 等大字段。因此对外容量仍应按场景定义，而不是只报一个人数。

## 3. 测试流量与安全措施

### 3.1 请求组合

压测器在每个虚拟用户内顺序请求，并加入 550–950ms 思考时间：

| API | 权重 | 是否写数据 |
|---|---:|---|
| `GET /api/projects` | 30% | 否 |
| `GET /api/tasks?status=ACTIVE` | 25% | 否 |
| `GET /api/user/balance` | 15% | 否 |
| `GET /api/films` | 10% | 否 |
| `GET /api/health` | 10% | 否 |
| `GET /api/client/update` | 10% | 否 |

阶梯为 1、5、10、20、35、50、75、100、150、200、250、300 VU。低档保持 15–20 秒，高档保持约 25 秒，每档之间降载 3 秒。

测试设置了自动停止条件：5 秒窗口失败率达到 2%、健康检查失败、P99 达到 8 秒超时，或 P95 连续两个窗口高于 2.5 秒。本次 HTTP 阶梯没有触发错误阈值；达到 300 VU 后因吞吐已经下降、主机负载明显超过 CPU 数量而停止继续升档。

### 3.2 未执行的危险/付费动作

本次明确排除了：

- 所有 `/api/generate/*` 付费生成；
- Seedance、Seedream、DeepSeek、Kimi 真实调用；
- 长视频上传、视频转剧本、海外转绘；
- 支付、短信、注册、积分扣费；
- Render Job 认领接口和任何 POST/PATCH/DELETE；
- MinIO 上传、下载和媒体中继压力。

这样得到的是 Web/鉴权/PostgreSQL/Redis/Nginx 控制面的容量，不是完整生成链路的容量。

## 6. SSE 结果

100 条 `/api/sse` 请求在 Nginx、Web 和 Redis 侧都已建立：Redis 客户端从 8 增至 108，Web 内存没有异常上升。但客户端一直等不到首个 SSE 数据块，无法把连接判为“业务可用”。

代码中每个 SSE 都 `duplicate()` 一个 Redis subscriber；生产主 location 没有关闭 `proxy_buffering`，响应也没有可靠设置 `X-Accel-Buffering: no`。结果是连接存在，但进度消息可能被代理延迟。这与“前端进度条生命周期要和后端同步”的产品目标直接冲突。

本次为防止 100 条长连接继续占用资源，测试端主动中止。Nginx 记录的 100 个 499 均来自这次主动清理，不是服务器故障。清理后 Redis 客户端恢复基线。

建议修改后单独做 SSE 回归：首次 `connected` P95 <1 秒、30 秒 heartbeat 最大空窗 <45 秒、100 连接维持 15 分钟、主动断开后 Redis 客户端在 10 秒内回落。

## 7. AI 与媒体链路为何不能按 HTTP 结果宣布通过

### 7.1 生产 Worker 实际并发为 1

生产 `WORKER_CONCURRENCY=1`，启动日志显示 text/image/video/voice 四类队列各自并发均为 1。历史资产生图平均执行约 34.2 秒；50 张图同时排队时，第 50 张仅等待前序任务就约 27.9 分钟，完成时间约 28.5 分钟，未计上游限流、重试和高峰波动。

### 7.2 Seedance 同步直连与限流未落在服务端

模型目录展示 Seedance 2.0 为 10 RPM、并发 2，但这些字段目前主要用于 UI 展示。部分视频路径直接在 Web 请求内调用上游，没有统一经过 BullMQ，也没有按 provider/model/key 执行全局并发信号量或 RPM token bucket。

50 人严格模式可能形成 50 个同步视频请求；快速模式默认每人 3 个，可能达到 150 个。即使生产有两个 active key，也不能在未确认独立上游额度的情况下把并发安全值简单翻倍。更可能先发生的是 429、两把 key 同时 cooldown、后续请求雪崩式失败，而不是本机 HTTP 进程先崩。

### 7.3 大文件会绕过本次安全内存曲线

多条视频接口会执行 `req.formData() → file.arrayBuffer() → Buffer.from()`，单文件最高 100MiB。Web 容器只有 384MiB，2–3 个最大文件同时进入就有 OOM 风险。

Seedance 链路还会把多张人物/场景参考图转 Base64 放进 JSON；Web `req.json()` 整体物化后，上游适配器再次 `JSON.stringify()`。本次只读请求的 Web 内存峰值 192.3MiB 对这类请求没有代表性。

### 7.4 任务生命周期已经存在生产残留

生产数据库发现 24 个 `PENDING` AI task 的 `timeoutAt` 已过期，最老约 10.8 天，但 BullMQ 已没有对应等待任务。当前没有 AI task 超时扫尾与 BullMQ/PG 对账，SSE 快照仍可能把这些记录当作活跃生成。

压力或部署中断后会出现前端永久“生成中”、任务表持续增长、恢复状态与真实队列不一致。这个问题不能靠加机器解决。

## 8. 主要风险与整改优先级

### P0：上线前必须处理

1. **所有 AI 路径统一准入控制。** 按 provider/model/key 在 Redis 中实现全局并发信号量与 RPM token bucket；视频、剧本分析、资产提取、分镜都不能绕过。
2. **大媒体请求改为流式或对象存储引用。** 禁止 Web 整体读取 100MiB 文件；禁止多张参考图 Base64 塞进同步 JSON。
3. **修复 AI task 生命周期。** 增加 timeout reaper、BullMQ/PG 定期对账、幂等终态写入；清理现有 24 条陈旧任务。
4. **处理 MinIO 128MiB 风险。** cgroup 历史 `memory.failcnt` 已非常高，本次未压媒体仍到 116.7MiB；至少提高配额并做真实上传/读取隔离压测。
5. **修复 SSE 实时性与清理。** 响应设置 `X-Accel-Buffering: no`，Nginx SSE location `proxy_buffering off`；提前注册 abort，确保退订一定执行。

### P1：容量扩展前处理

1. Web 和 Worker 的 PostgreSQL Pool 都是 `max:80`，理论合计 160，高于 PostgreSQL `max_connections=100`。建议先调整为 Web 20、Worker 10，并为管理连接保留余量；扩副本前引入 PgBouncer。
2. `/api/projects`、episodes 等列表避免 `SELECT *` 返回剧本大字段，改为摘要 DTO、分页和按需详情读取。
3. `/films`、groups、任务/事件列表增加分页、上限和保留策略。
4. `/api/health` 目前只证明 Web 进程存活，增加 readiness：PostgreSQL、Redis、队列写入能力、任务积压年龄。
5. 增加 Nginx `limit_conn`、`limit_req`、上传临时目录和磁盘水位保护，防止少量客户端消耗所有连接或 18GiB 剩余磁盘。

## 9. 建议的下一轮验证

完成 P0 后，在隔离 staging 中用确定性 AI stub 模拟真实延迟、429、进度事件和失败重试，再做完整生命周期压测：

1. 50 个独立账号，而不是共享会话。
2. 每个账号使用含真实规模剧本、20–50 个资产、镜头和历史成片的项目。
3. 50 条 SSE 持续 30 分钟，并持续发布只属于各自用户的进度事件。
4. 图片/文本/视频分别按目录并发上限提交，验证超额请求可靠排队，不直接冲上游。
5. 随机终止 Web/Worker、断开 Redis、模拟上游 429，验证前后端最终一致、积分只扣一次、任务必达终态。
6. 最后只用少量真实付费调用验证上游适配，不在生产用 50 路真实生成寻找极限。

## 10. 最终结论

当前服务器的轻量控制面不是 50 人上线的阻碍：**50 个高活跃客户端实测 P95 96ms、0 失败，性能充足。** 本次合成只读流量的吞吐极限约为 244 RPS，250 VU 后开始饱和；推荐将同类轻量流量的运行安全线控制在 150 VU / 175 RPS 左右，并保留真实大字段与后台任务余量。

真正限制产品并发的不是这个 HTTP 数字，而是：Seedance/DeepSeek 等上游并发没有服务端统一门控、Web 整体缓冲大媒体、MinIO 内存过紧、AI task 缺乏超时对账，以及 SSE 被代理缓冲。**所以可以发布“50 人同时在线浏览可承载”，不能发布“50 人同时生成可承载”。**
